# SHIFT REVERSI Constitution

## Core Principles

### I. ロジック分離（DxLib 非依存コア）

- ゲームルール・盤面状態・イベント抽選・CPU 思考は、DxLib のヘッダや型に一切依存しない
  純粋な C++20 の静的ライブラリ（以下「コア」）として実装しなければならない（MUST）。
- 描画・入力・画面遷移（以下「プレゼンテーション層」）はコアの公開 API のみを呼び出す。
  コアからプレゼンテーション層への依存は禁止（MUST NOT）。
- 乱数はシード注入可能なインターフェース経由で扱い、テストで再現できること（MUST）。

理由: ルールの正しさを DxLib なしで自動検証でき、描画の変更がルールを壊さないようにするため。

### II. ルールの自動テスト必須（NON-NEGOTIABLE）

- 着手判定・反転・行列スライド（回り込み）・区画回転・パス・前倒しイベント・終局判定・
  イベント抽選（無変化イベント除外を含む）は、コンソール型テスト exe で自動検証しなければ
  ならない（MUST）。
- テスト exe は失敗時に非ゼロ終了コードを返すこと（MUST）。
- テストが 1 件でも失敗している変更はコミット／マージしてはならない（MUST NOT）。
- バグ修正時は、再現するテストを先に追加する（SHOULD）。

理由: 「動く盤面」は手作業では見落としやすいエッジケースが多く、回帰を機械的に防ぐため。

### III. 仕様忠実

- 実装は承認済みの spec.md に記載されたルール・画面・機能のみを対象とする（MUST）。
- 仕様にない機能（Undo、ポーズ、サウンド、オンライン対戦等）を独断で追加してはならない
  （MUST NOT）。追加が必要と判断した場合は spec を更新しユーザー承認を得る。

理由: インタビューで確定した要件と成果物の一致を保証するため。

### IV. 単純さと依存最小化

- 外部依存は DxLib と C++ 標準ライブラリのみとする（MUST）。
- 画像・音声素材ファイルは使用せず、図形描画とフォント描画のみで表現する（MUST）。
- 抽象化は実際に 2 箇所以上で必要になるまで導入しない（YAGNI, SHOULD）。

理由: 学校課題・ポートフォリオとしてビルド再現性と可読性を最優先するため。

### V. 応答性とパフォーマンス

- ゲームループは 60 FPS を目標とし、1 フレームの処理でメインスレッドを 16ms 以上
  ブロックしてはならない（MUST）。
- CPU 思考は最大 3 秒で打ち切り、ワーカースレッド等で実行して描画・入力を止めない（MUST）。
- アニメーション中に盤面状態とのずれが生じないよう、表示状態はコアの確定状態から導出する
  （MUST）。

理由: 思考中やアニメーション中にウィンドウが固まる体験を防ぐため。

### VI. 日本語ファースト

- ゲーム内 UI テキストは日本語とする（MUST）。
- spec / plan / tasks 等のドキュメントは日本語で記述する（MUST）。コード識別子は英語。

理由: 想定プレイヤーおよび提出先が日本語話者であるため。

## 技術的制約

- 開発環境: Visual Studio 2026、MSVC、C++20、x64（Debug / Release）。
- ライブラリ: DxLib（VisualC++ 版）のうちビルドに必要なヘッダと x64 用 lib を `third_party/DxLib/` に
  同梱し、クローン直後にビルドできること。DxLib ライセンス文書が求める著作権表記を
  `THIRD_PARTY_NOTICES.txt` に含めること。取得・整理手順は `tools/` のスクリプトで再現可能にすること。
- 提出物: `release/ShiftReversi.exe`（テスト成功後に `tools/make-release.ps1` で生成）を同梱し、
  クローン後にビルドなしで遊べること。
- 実行形態: 1280×720 ウィンドウモード、マウス操作のみ。
- ソリューション構成: コア（静的ライブラリ）、ゲーム本体（DxLib 使用 exe）、テスト（コンソール exe）
  の 3 プロジェクトを基本とする。

## 開発ワークフローと品質ゲート

- Spec Kit の手順（constitution → specify → clarify → plan → tasks → implement）に従う。
- 各コミット前に: (1) Release|x64 で全プロジェクトがビルド成功、(2) テスト exe が全件成功。
- プレゼンテーション層の変更は、ゲームを起動して該当画面の動作を目視確認する。
- 未実施の確認を「成功」と報告してはならない。

## Governance

- 本憲章は他のすべての開発慣行に優先する。
- 改訂は理由・影響範囲を記載した上でユーザー承認を得て行い、Sync Impact Report を更新する。
- バージョニング: 原則の削除・再定義は MAJOR、原則・節の追加や大幅拡張は MINOR、
  文言修正は PATCH。
- plan.md の Constitution Check で各原則への適合を確認し、逸脱は Complexity Tracking に
  正当化を記載する。
